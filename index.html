01 / 先说结论

它到底改变了什么？

如果把“智能体接仓库”说得再直白一点：它把一次口头请求，变成了一条有授权、有隔离、有审查的交付流水线。人仍然掌握方向和最终决定，重复劳动交给后台。

1

对仓库：多一个按规则接单的协作者

它不睡觉，也不会因为上下文切换而忘记讨论。收到请求后按同一套流程执行，改完把 PR 放在那里。

2

对人：只做两件事

把要求说清楚，以及审查结果。不用盯进度，不用重复解释背景，也不需要在聊天窗口和代码仓库之间搬运信息。

3

对团队：每一步都留下证据

谁发起的、为什么受理、改了哪些文件、跑了什么检查、谁合并的，都能从 Issue、PR 和面板里对上。

02 / 它是什么

不是聊天助手，
而是一个交付流程

dsh-superagent 是运行在 DeepSeek Harness 里的研究型插件。它监听 GitHub 事件，把被授权的请求变成工单，再交给一个在工作目录里动手的编码智能体。

A普通聊天助手

  • 入口聊天窗口，离开窗口上下文就断了
  • 工作给建议、贴代码片段
  • 交付一段文字，需要人再搬进仓库
  • 结束回答完就结束
  • 权限通常没有仓库写权限

Bsuper-agent

  • 入口Issue / PR，讨论和代码在同一个地方
  • 工作在独立目录里读、改、跑检查
  • 交付分支 + Pull Request + 验证说明
  • 结束停在“等人审查”，不是自说自话
  • 权限真实写权限，但受允许列表、策略和人工合并约束
!

它不是什么

不是自动合并机器人，不是万能聊天助手，也不是没有边界的后台程序。它只在被授权时行动，只把结果做到“可审查”，最后一步始终交给人。

03 / 为什么值得

把智能体装进流程，
而不是放进口头承诺

智能体最大的风险不是“不会做”，而是“做了但没人知道它做了什么”。super-agent 把权限、隔离、审查和沟通规则一起打包，让自动化真正可以交给团队使用。

01

请求 → 可审查的变更

不是给一段建议，而是给出能看 diff、能跑测试、能合并或拒绝的 PR。

02

上下文留在原线程

后续讨论会回到同一个工单，不需要重新 @，也不用把背景再讲一遍。

03

权限关进流程

允许列表决定谁能发起；策略决定哪些能自动做；人工合并保留最后一道闸门。

04

打扰降到最低

只在收到、就绪、需要决定或做不下去时说话，其余时间把进度留在面板和 PR 里。

04 / 怎么工作

一次请求，六个步骤

对发起人来说，体验只有三件事：提请求、等结果、审查合并。中间那些 Trigger、Eval、Ticket、Executor，是系统为了保证“做对事”而加的内部结构，不需要你记住。

  1. 点名

    允许列表里的同事在 Issue 里 @ 智能体，写清楚目标、范围和验收标准。

  2. 接单

    GitHub Source 把事件变成 Trigger，检查它是否真的在请求工作。

  3. 判断

    Eval 检查发起人、请求强度和范围。接受后创建 Ticket；不确定时只观察。

  4. 开工

    Executor 在专属 git worktree 中读代码、改代码、跑检查，不碰主分支。

  5. 交付

    提交到 agent/<工单短名> 分支，开 PR，回原 Issue 报告。

  6. 收尾

    人审查、合并。后续评论继续回到同一工单，不需要重新发起。

?

如果中途需要人做决定呢？

它会停下来问一个具体问题，把选项和影响说清楚，而不是猜一个方向继续做。问题会出现在原对话里，并在面板中标为“等待回答”。

05 / 结构

它连接了什么？

左边是人和 GitHub，右边是真正动手的执行环境，中间是负责判断和授权的 super-agent。三者之间只通过受控的入口和出口交换信息。

08 / 用途

这个仓库，
到底有什么用？

它既不是产品，也不是玩具。它是一块“公开的试验田”，让维护者、接入团队和第一次接触 super-agent 的人，都能在同一组真实记录上达成共识。

A

维护者的低风险金丝雀

用真实 GitHub 事件验证 Source、Eval、Ticket、Executor、回信和面板是否协同工作。出错时可放心重试，不涉及生产数据。

B

接入团队的参照样例

接入后大概会看到什么状态、Issue 会怎么被回复、PR 长什么样、哪些动作需要人，都可以先在这里看一遍。

C

新读者的证据链

从 Issue 到 PR 再到合并，每一步都公开可查。不是“相信我们”，而是“你自己点开看”。

09 / 边界

它很强，
但边界必须说清楚

一个能推分支、开 PR 的智能体，已经不是一个“玩具”。下面这些限制不是免责声明，而是使用它时必须理解的前提。

研究原型，不是生产软件

行为和接口都可能变化。先在低风险仓库里验证，再考虑扩大使用范围。

写权限是真实的

它在操作者的 OS 用户下运行，策略和工具限制不是强安全沙盒。需要强隔离时，应使用专门的 OS 账号。

合并必须由人完成

本部署没有配置自动合并。智能体负责做到“可审查”，人负责最后的判断。

不要在公开仓库放敏感信息

Issue、评论和 PR 都是公开的。不要粘贴密钥、客户数据、私有链接或内部凭据。

接入原则：先窄后宽。先允许少数账号、先用 observe、先不给自动合并，确认行为符合预期后再扩大。

10 / 常见问题

你可能想先问清楚的事

如果下面没有回答你的问题，可以直接在 Issue 里问；允许列表内的账号 @ 智能体即可。

它会自己合并 PR 吗？

不会。本部署没有配置自动合并，PR 会停在“等待审查”，由人决定合并、要求修改或关闭。这是故意保留的人类闸门。

为什么它的 GitHub 回复开头是英文？

那是固定的透明说明：“This is by an automated agent, not a human.”，用于避免被误认为真人。正文会跟随请求者的语言；这次请求是中文，所以说明和回复主体都是中文。

为什么接单之后看起来没动静？

它被设计成“只在需要人时说话”。收到请求时确认一次，执行期间保持安静，就绪或需要决定时再报告。进度留在 PR 和 Superagent 面板里，不靠刷消息证明自己在工作。

我可以直接让它改东西吗？

需要满足两个条件：你的 GitHub 账号在允许列表里，并且请求明确 @ 了智能体。当前允许列表只有 @hualidezhen；不在列表里的请求默认不会被受理。

PR 合并后还能继续追问吗？

可以。Issue 和 PR 的讨论会继续送到同一个工单，不需要重新 @。如果请求超出原工单范围，执行者会把消息交回评估流程，而不是擅自扩大范围。

它和“自动写代码的机器人”有什么区别？

区别在流程：它有来源、授权、工单、隔离目录、审查和回信通道，并且明确什么时候应该停下来问人。它追求的不是“全自动”，而是“在人的控制下尽可能自主”。

11 / 开始使用

想试一次？
按这三步来

这是一个公开仓库，允许列表内的账号可以直接发起请求。第一次建议从一个小而明确、可验证的改动开始。

  1. 说清楚要什么

    新建 Issue，或直接在已有讨论里回复。写清目标、范围、验收标准，并 @ 智能体。

  2. 等它确认，然后去做别的事

    收到确认后不需要盯着。它会在就绪、需要决定或做不下去时再出现。

  3. 审查 PR，做最后决定

    看 diff、跑你关心的检查，然后合并、要求修改或关闭。后续意见留在原线程即可。
